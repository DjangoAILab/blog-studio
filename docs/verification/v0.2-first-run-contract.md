# v0.2 First-run State Contract Verification

Verified on 2026-08-05 on branch `codex/v0.2-site-foundation`.

## Contract

`GET /api/setup/status` is public because it must guide an owner before a
browser session exists. It exposes three independent, non-sensitive facets:

- `credentials`: `ready` or `not-ready`;
- `configuration`: `valid` or `invalid`;
- `site`: `registered`, `not-registered`, or `unavailable` while configuration
  is invalid.

An incomplete facet includes one stable action identifier:
`initialize-owner-credentials`, `repair-configuration`, or `discover-site`.
The response never includes database/configuration paths, parser errors,
workspace roots, environment values, credentials, or provider diagnostics.

`ready` is true only when owner credentials are initialized, configuration is
valid, and at least one Site is registered. This is readiness for the normal
product journey, not a deployment or release authorization.

## Invalid-configuration behavior

Invalid Site configuration no longer terminates the HTTP process before the
owner can understand the state. Instead:

- `GET /api/health` returns HTTP 503 with `CONFIGURATION_INVALID`, so a bad
  candidate cannot pass deployment health checks;
- setup status, authentication status, password login, and the static client
  remain available;
- all Site/content/preview/ChangeSet/release operations remain unavailable and
  return HTTP 503 after authentication;
- the detailed exception is confined to redacted server logs for trusted-host
  diagnosis.

This is a fail-closed recovery surface. It does not load a partial set of
workspaces or allow operations against a stale configuration.
