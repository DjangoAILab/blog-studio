# v0.2 Owner Authentication Verification — 2026-08-04

## Scope

This evidence covers the owner credential lifecycle, not Site onboarding or
the remaining v0.2 release gates. The implementation keeps a v0.1 deployment
token only as an optional migration fallback while the database has no owner
credential. Initializing the owner immediately disables that fallback.

## Security model verified

- Browser routes can report initialization state but cannot initialize or reset
  ownership.
- `auth init` refuses replacement; `auth reset` requires trusted host access.
- CLI password input is hidden and confirmed on a TTY, or read from stdin or a
  regular file inaccessible to group/other users. Plaintext command-line
  password options and ambiguous sources are rejected.
- Passwords use a randomized, versioned scrypt verifier with `N=32768`, `r=8`,
  `p=1`, a 16-byte salt, and a 32-byte derived key. Verification uses
  constant-time key comparison.
- SQLite stores only password verifiers and SHA-256 hashes of random 32-byte
  browser session tokens.
- Password change requires a valid session plus the current password. Change
  and CLI reset rotate the credential generation and delete every existing
  server-side session in the same database transaction.
- Login failures are bounded by an in-memory five-attempt/five-minute limiter.
  A structured log-capture regression proves password, current/new password,
  verifier, session token, legacy token, request/response cookie, CSRF, and
  authorization fields are replaced by the configured redaction censor.

## Automated evidence

Focused HTTP, service, persistence, CLI, and API tests:

```text
corepack pnpm --filter @blog-studio/studio test
```

Current result: PASS, 11 test files and 61 tests. The focused runs and full
repository check also passed.
Coverage includes:

- uninitialized status and refused browser ownership claim;
- one-time CLI initialization and weak/mismatched/unsafe input;
- randomized verifier and malformed-verifier rejection;
- correct/wrong password behavior and no session on failure;
- automatic legacy-token disablement after initialization;
- server-side session expiry and raw-token non-persistence;
- five failed requests followed by HTTP 429;
- re-authenticated browser password change and all-session revocation;
- CLI reset and all-session revocation;
- stale credential-generation rollback.

The production build plus Playwright journey starts from an empty SQLite file,
initializes the owner through the compiled CLI, logs in through the password UI,
creates/edits/reloads/previews/discards a draft, changes the owner password,
logs out, and logs back in with the replacement password:

```text
corepack pnpm --filter @blog-studio/studio e2e
```

Result: PASS, desktop Chrome, 1 end-to-end journey in 7.5 seconds. No publisher
or production-blog operation was invoked.

The production-shaped Quick Start, container, and operations smokes initialize
an empty mounted database through the compiled CLI, log in only with the owner
password, preserve the session and draft across a container restart, and retain
the credential verifier across a checksum-validated backup/restore:

```text
CI=true corepack pnpm quick-start:smoke
CI=true BLOG_STUDIO_SMOKE_IMAGE=blog-studio:quick-start corepack pnpm container:smoke
CI=true BLOG_STUDIO_SMOKE_IMAGE=blog-studio:quick-start corepack pnpm operations:smoke
```

Result: PASS. The default Compose contract no longer mounts or requires the
legacy token secret.
