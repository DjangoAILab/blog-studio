# v0.2 Container and Operations Verification

Verified on 2026-08-04 on branch `codex/v0.2-site-foundation`.

## Default deployment contract

- Docker Compose requires only a cookie secret for core authentication. The
  v0.1 opaque auth-token secret is absent from the normal deployment path.
- The first owner password is initialized from a trusted container invocation
  before Studio starts. Interactive use hides and confirms the password;
  automation may use stdin without placing it in the process argument list.
- The compiled server keeps legacy live-tree release disabled unless the
  operator explicitly sets the temporary compatibility environment switch.
- Primary README and self-hosting documentation describe password login,
  credential status/reset, Site/ChangeSet terminology, Markdown fallback, and
  immutable committed-revision release.

## Reproducible evidence

```sh
docker compose config --quiet
CI=true corepack pnpm quick-start:smoke
```

Result: PASS. From an empty database, the smoke builds the production image,
initializes the owner through the compiled CLI, starts the hardened Compose
service, logs in with the password, discovers/edits durable content, loads a
real preview, proves the Git tree is untouched, and keeps publishing disabled.

```sh
CI=true BLOG_STUDIO_SMOKE_IMAGE=blog-studio:quick-start \
  corepack pnpm container:smoke
```

Result: PASS. The image runs as non-root with a read-only root filesystem and
no Linux capabilities; health, password authentication, durable draft state,
clean SIGTERM, and cold container recreation passed. Before recreation the
smoke seeded an interrupted preview sandbox in the persistent data mount; the
new process removed it before becoming healthy without disturbing the draft.

### Linux amd64 acceptance on `hermes-host`

The current branch was copied to an isolated directory created with `mktemp`
and verified on Debian 13, Linux 6.12, x86_64, Docker 26.1.5, 8 CPUs, and 24 GB
RAM. No production checkout, running service, Site content, or Provider was
mounted or contacted.

Docker Hub's anonymous-token endpoint reset the connection from this host. The
same locked official Node image was therefore pulled through Public ECR; its
manifest digest exactly matched the Dockerfile pin
`sha256:0340fa682d72068edf603c305bfbc10e23219fb0e40df58d9ea4d6f33a9798bf`.
Only the registry hostname was substituted in the streamed acceptance
Dockerfile; source, tag, manifest, build stages, and runtime instructions were
unchanged.

```sh
docker build --pull=false -f - \
  -t blog-studio:v02-acceptance-2e9c726 .

BLOG_STUDIO_SMOKE_IMAGE=blog-studio:v02-acceptance-2e9c726 \
  BLOG_STUDIO_SMOKE_PORT=14312 ./scripts/container-smoke.sh
```

Result: PASS. Image `sha256:c78938b2ca43fc7e73f2a33f9aff8685bbbfc0e0df1f10e3224e7936e353564a`
built successfully. The first smoke exposed that its 20-second wait window was
shorter than the image's 30-second health interval. The script now permits a
60-second cold-host window and prints Docker health state on timeout. The rerun
passed non-root execution, read-only root, health, owner authentication,
durable draft, SIGTERM, cold recreation, interrupted-preview recovery, and the
fail-closed invalid-configuration state.

```sh
CI=true BLOG_STUDIO_SMOKE_IMAGE=blog-studio:quick-start \
  corepack pnpm operations:smoke
```

Result: PASS. An online SQLite backup and checksum were created, state was
destructively changed in an isolated fixture, the validated backup was restored,
and password login plus the prior draft survived a cold restart. No remote
Provider or production Site was contacted.
