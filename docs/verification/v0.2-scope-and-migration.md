# v0.2 Scope, Canonical Data, and Migration Verification

Verified on 2026-08-05 on branch `codex/v0.2-site-foundation`.

## Shipped scope

The production Studio client and HTML entry contain no statistics, word
frequency, AI-analysis, Agent, MCP, or future landing-page controls. A
case-insensitive source scan of `apps/studio/src` and `apps/studio/index.html`
returned no matches for those product terms. Future architecture remains
documentation-only and is explicitly deferred by the release checklist.

## Canonical-data boundary

Markdown, Site configuration, resources, and Git remain canonical. SQLite owns
only operational identity, sessions, working copies, Site registrations,
ChangeSets, jobs, and release records. The Site registration, working-copy,
preview, ChangeSet preparation, backup/restore, and reference-Site tests compare
canonical file bytes and Git status before and after operations. Only an
explicitly reviewed ChangeSet apply writes Markdown; SQLite migration never
does.

The real reference-Site test discovers and registers `wj2015-blog` against a
temporary SQLite database, then proves its Git HEAD, clean status, and canonical
Hexo configuration hash are identical. The current production upgrade baseline
independently recorded the same workspace revision and clean status before and
after the Studio-only cold start.

## v0.1 compatibility

```sh
corepack pnpm --filter @blog-studio/config test
corepack pnpm --filter @blog-studio/persistence test
BLOG_STUDIO_REFERENCE_ROOT=/path/to/wj2015-blog \
  corepack pnpm --filter @blog-studio/studio exec vitest run \
  server/test/reference-site.test.ts
```

Result: PASS. Coverage proves:

- a v0.1 workspace-only configuration remains a valid Site discovery input;
- an unversioned v0.1 SQLite database upgrades in transactions;
- draft version, front matter, body and saved time remain intact;
- existing release records, manifests, stages, events and status remain intact,
  while new immutable-source columns are added as null;
- every statement in a failed migration rolls back to the previous schema
  version;
- future schemas are rejected rather than partially opened;
- the real 93-article reference blog is discovered and registered without
  modifying content, configuration, Git HEAD, or Git status.

The home-server pre-upgrade archive and checksum are recorded separately in
[`v0.2-home-server-candidate.md`](./v0.2-home-server-candidate.md); they preserve
the complete v0.1 operational database, adoption configuration, workspace and
Git data before the production migration.
