# v0.2 Top-Navigation Redesign Brief

**Status:** owner-approved implementation target. **Recorded:** 2026-08-04.
**Approved:** 2026-08-05.

This brief supersedes the permanent-rail spatial model in the earlier visual
candidates. It records durable product and visual constraints; it is not yet a
production implementation target.

## Product hierarchy

The authenticated Studio shell has three primary destinations, in this order:

1. **Site** — the root object and default home. It owns identity, URL,
   capabilities, diagnostics, content, previews, ChangeSets, and release
   targets. The first screen for the existing owner is the overview for
   “王二的博客”, not a generic dashboard.
2. **Content** — the unified published, draft, and working-copy library plus
   editing and preview journeys scoped to the selected Site.
3. **Settings** — owner security, providers, system behavior, and advanced
   workspace diagnostics. Site metadata remains reachable from the Site
   object rather than being mixed with system-wide settings.

`Prepare changes` is a persistent cross-cutting action. It opens a ChangeSet
review but is not a fourth navigation destination. Remote release remains a
separate action after a reviewed local revision exists.

## Resource behavior

Resources are infrastructure, not a primary product destination. The Studio
does not expose a standalone resource library in its normal navigation.

- Upload is contextual to an article, Site identity field, or other consuming
  surface.
- Identical bytes reuse an existing immutable resource automatically through a
  content hash; the owner sees a lightweight “reused existing file” result.
- Portable source syntax remains canonical. Associations and derived indexes
  may live in SQLite but are rebuildable.
- Policy failures, quarantine, unresolved references, and orphan candidates
  surface in the editor, diagnostics, or ChangeSet review only when action is
  needed.
- Advanced resource inspection can exist under Site diagnostics without
  becoming ordinary navigation.

## Navigation and material direction

Use one persistent top navigation for the shallow information architecture.
The left side holds the product identity and current Site switcher; the middle
holds `站点 / 内容 / 设置`; the trailing side holds persistent utilities and
`准备更改`. Narrow layouts may collapse destinations into a compact adaptive
control, but their order and meaning stay stable.

The application background is one continuous content field. Do not create an
unexplained color strip above the shell, an app-card-on-colored-canvas framing,
or competing left/right material blocks. Liquid Glass is restricted to the
top functional layer and transient sheets. Site, article, preview, and diff
content use stable standard surfaces with clear text contrast.

## Research grounding

- Apple Human Interface Guidelines: Liquid Glass is a functional layer for
  navigation and controls, not the content layer; use it sparingly and preserve
  a clear hierarchy.
- Apple layout and toolbar guidance: align controls consistently, keep the bar
  materially uniform, and use scroll-edge transitions rather than an arbitrary
  background division.
- IBM Carbon global-header guidance: a header-only shell is suitable when a
  product has few primary sections; product navigation belongs toward the
  leading side and system utilities toward the trailing side.

## Visual selection gate

The production rewrite uses the owner-selected, refined **Focused Workbench**
direction: one compact floating top bar, a continuous warm content field,
optically aligned Site content, grouped rounded lists, and stable opaque content
surfaces. The target is a design system rather than a screenshot trace; Content,
Settings, editor/preview, ChangeSet review, first run, and mobile adaptation must
apply the same hierarchy and geometry.

The implementation kernel is intentionally stack-preserving:

- `@base-ui/react` supplies accessible unstyled primitives for the Site switcher,
  menus, popovers, dialogs, and segmented navigation;
- `motion` supplies interruptible layout, shared-element, presence, and reorder
  motion, with user reduced-motion settings respected globally;
- plain CSS semantic tokens supply material, typography, spacing, radius,
  focus, and non-blur fallbacks; the existing Vite/React application does not
  migrate to Tailwind or a framework-specific component kit;
- glass is a progressive enhancement for navigation and transient controls,
  never a dependency for content readability or interaction.
